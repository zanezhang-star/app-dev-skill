# 真实反馈与验证收敛

本参考用于会改变交付结论的场景：真实运行反馈、复杂状态语义、合同/缺陷边界、第二轮后的微复核，以及按变更链选择测试。主控只在触发相关场景时加载，不把这些细节默认复制给每个角色。具体失败定位和局部修复使用 `diagnosis-matrix.md`。

## 1. 真实运行验收失败优先

真实安装、真实数据、真实权限、真实 UI、真实 CLI、第三方 API、数据迁移、真实数据库或生产副本的只读观察，若与核心 AC 冲突，优先级高于此前自动化、Mock、构建和 Quality 结论。

收到可信用户反馈时，无需等待根因明确即可使**受影响 AC 和交付结论**失效；不相关的历史测试证据可以保留，但不能用来覆盖当前失败。

主控必须：

1. 在任务资料中记录 `real_world_validation_failed`：环境、输入、观察、受影响 AC 和证据位置。
2. `ready_for_merge` / `verification_in_progress` 立即失效：
   - 行为明确违反已批准 AC：回到 `development_in_progress`；
   - 暴露出需求含糊或新增产品语义：回到 `analysis_in_progress`，按下表判断是否增加合同版本。
3. 按 `diagnosis-matrix.md` 锁定失败维度并建立最小复现；不能复现时记录环境差异、缺失证据和下一次观察方法，不得维持原 PASS。
4. 修复后先跑直接变化链，再在原真实环境或等价环境重新验收受影响 AC。
5. 不得以此前自动化 PASS、旧 Quality PASS 或“多数场景正常”替代本次真实运行失败的闭环。

适用于 Web、Desktop、Mobile、插件、CLI、数据迁移、权限系统、第三方集成和本地数据库分析。

## 2. 状态语义矩阵

当功能存在多个数据来源、处理阶段、降级链、默认值、空值、零值、历史值、权限值或可重试错误时，Product/Architect 必须建立状态语义矩阵；简单二态功能不强制，避免流程膨胀。

矩阵至少包含：

| 输入条件 | 内部状态 | 用户可见状态 | 可否重试 | 是否允许默认值 |
|---|---|---|---|---|
| 示例：无记录 | `empty` | 暂无数据 | 否/按产品规则 | 不得伪装为 0 |
| 示例：读取失败 | `unavailable` | 数据暂不可用 | 是 | 不得降级为空数据 |

按项目需要增加：来源/时间范围、权限、缓存/历史标记、错误码、日志/审计和恢复动作。

Quality 必须检查：

- 未知是否被压成零；
- 不可读是否被压成无数据；
- 未处理是否被压成失败；
- 历史数据是否被展示为实时；
- 禁用是否被展示为不支持；
- 默认值是否掩盖权限、价格、数据质量或外部系统问题。

## 3. 合同变更与缺陷修复

判定原则：**先问预期行为是否已被当前批准合同唯一确定。** 若已唯一确定而实现不符，是 defect；若需要定义新的用户可见语义，是合同变更。

| 变化类型 | 是否增加合同版本 |
|---|---|
| 实现未满足既有、明确的 AC | 否，按 defect 修复 |
| 只修复与既有 AC 一致的边界条件 | 否 |
| 新增用户可见行为 | 是 |
| 修改默认值、空值、未知值或回退语义 | 是 |
| 改变安全、权限、数据保留、删除、唯一性或计费语义 | 是 |
| 原合同沉默/含糊，用户反馈首次确定产品语义 | 是 |
| 仅补充复现步骤、测试证据或不改变行为的说明 | 否 |

不升级合同不等于不留痕：defect 仍须记录受影响 AC、最小复现、修复 diff 和复测证据。升级合同时，旧批准版本立即失效并重新等待用户授权。

## 4. 第二轮后的 Micro-review

默认两轮完整 Quality 上限不变。第二轮若只剩一个或一组同根因问题，可在**全部**条件满足时使用一次 micro-review：

- 无需求范围扩张，合同版本不变；
- 修改面明确、受限，可列出全部相关文件和函数；
- 有确定性 RED 测试或等价失败复现；
- 修复后相同验证 GREEN；
- 不涉及安全、权限、不可逆数据、生产迁移、计费语义或外部副作用；
- 第二轮完整 Review 已对其他 AC 给出有效结论，且这些证据未因修复过期。

执行方式：

1. Developer 只修该 issue，主控核对 scoped diff 和 RED→GREEN 证据。
2. 新的独立 Quality 只读取：issue、受影响 AC 摘要、相关 diff/代码、新增或受影响测试及原始结果。
3. 不重读无关项目资料、完整聊天或全部合同；信息不足时可按 May Read 扩展并记录原因。
4. micro-review 只关闭该 issue，不重写第二轮对其他 AC 的结论；主控组合“第二轮未受影响结论 + micro-review”形成最终闸门。
5. 每个任务最多一次。条件不满足、范围扩大、证据过期或 micro-review 失败，立即 `blocked`，等待用户决定；不得继续形成第四轮循环。

Micro-review 必须独立于 Developer，也不等同于跳过复审或无限增加 Quality 轮次。

## 5. 测试去重与阶段闸门

测试选择按**可执行代码和风险面变化**决定，不按文件保存次数、报告更新时间或状态迁移次数决定。

| 变化类型 | 必须执行 | 默认不重复执行 |
|---|---|---|
| 仅任务资料、文档、`status.yaml` | 结构/引用校验、`git diff --check`、需要时检查 packet freshness | 应用测试、全量测试 |
| 只改测试 | 新增测试及受影响测试链；确认 RED/GREEN 语义有效 | 无关模块测试 |
| 改业务代码 | focused test、直接依赖链和对应 AC 验证 | 每次小编辑都跑全量 |
| 修复批次完成 | 受影响回归链、编译/静态检查 | 与变更无关的重复全量 |
| 独立 Quality 或提交/合并闸门 | 运行一次项目约定的广测试；若无 canonical suite，记录替代证据和限制 | 同一源码快照上重复跑相同广测试 |

若源码、依赖、测试或运行环境未变化，任务资料更新不会让已有应用测试结果失效；但 must-read/状态变化仍可能使角色 packet 过期，需要重新生成或检查 freshness。任何跳过都要写明“风险面未变化”的依据，不能用测试去重掩盖缺失测试。
